Module 4.1: Cart Persistence
Below are suggested steps to implement automatic cart persistence for visitors, keeping the rest of the module plan intact.
1. Create an API route to update a visitor’s cart
Add a new handler at pages/api/visitor/updateCart.ts.
It should:
Require POST.
Read the JWT from the Authorization: Bearer header (same as in validate.ts).
Verify the token using process.env.SUPABASE_JWT_SECRET.
Extract visitor_id from the token.
Update the cart column of the visitors table for that visitor_id.
Return success or an error.
init.ts already inserts a visitor with cart: null on first registration.
validate.ts returns the cart when validating the JWT, so the new endpoint should mirror this pattern.
2. Sync the cart on the client
Within a React effect that has access to both the JWT and the cart items:
Import useCartStore and select items.
Debounce or throttle to avoid rapid requests.
Whenever items changes and the visitor is authenticated, POST the cart JSON to /api/visitor/updateCart with the
Handle errors gracefully (logging, possibly retrying).
The VisitorContext already hydrates visitorData with the cart on validation, so an additional effect in this context (or a hook used globally) can watch for cart changes.
3. Keep module flow unchanged
No structural changes are needed for modules 5‑8. They already assume the visitors table holds the latest cart so that module 6 can merge it into a user profile. Adding the update endpoint and client sync simply ensures the cart field remains current.
4. Development tips
Reuse the service‑role Supabase client from lib/supabaseClient.ts.
Reuse JWT verification logic from validate.ts to keep security consistent.
Document the new endpoint and any new environment variables.
Write a small test or console log to confirm that cart updates appear in the visitors table.
By isolating the cart synchronization to a dedicated API route and a lightweight client effect, you can add persistent cart storage without altering the existing module plan. This keeps the upcoming modules (5‑8) focused on user authentication and session management while ensuring visitor carts are always saved and ready to merge when a visitor becomes a full user.

Module 6 Overview
Module 6 bridges visitor checkout into authenticated user checkout. It starts immediately after Module 5 (when the user opts to “Check out as user”) and concludes once Stripe’s checkout session is created. Modules 7–8 then manage Supabase session persistence, while Modules A–D handle the Stripe flow.
Module 6 Boundaries with Other Modules
Modules 7–8: Begin only after 6b or 6d completes. They rely on the Supabase session created or confirmed during Module 6 to handle ongoing session management and expiry.
Modules A–D: Assume the Stripe checkout session has been created in 6d. They process payment, handle webhooks, and manage post‑checkout steps.
