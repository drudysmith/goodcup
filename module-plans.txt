Module 4.1: Cart Persistence
Below are suggested steps to implement automatic cart persistence for visitors, keeping the rest of the module plan intact.
1. Create an API route to update a visitor’s cart
Add a new handler at pages/api/visitor/updateCart.ts.
It should:
Require POST.
Read the JWT from the Authorization: Bearer header (same as in validate.ts).
Verify the token using process.env.SUPABASE_JWT_SECRET.
Extract visitor_id from the token.
Update the cart column of the visitors table for that visitor_id.
Return success or an error.
init.ts already inserts a visitor with cart: null on first registration.
validate.ts returns the cart when validating the JWT, so the new endpoint should mirror this pattern.
2. Sync the cart on the client
Within a React effect that has access to both the JWT and the cart items:
Import useCartStore and select items.
Debounce or throttle to avoid rapid requests.
Whenever items changes and the visitor is authenticated, POST the cart JSON to /api/visitor/updateCart with the
Handle errors gracefully (logging, possibly retrying).
The VisitorContext already hydrates visitorData with the cart on validation, so an additional effect in this context (or a hook used globally) can watch for cart changes.
3. Keep module flow unchanged
No structural changes are needed for modules 5‑8. They already assume the visitors table holds the latest cart so that module 6 can merge it into a user profile. Adding the update endpoint and client sync simply ensures the cart field remains current.
4. Development tips
Reuse the service‑role Supabase client from lib/supabaseClient.ts.
Reuse JWT verification logic from validate.ts to keep security consistent.
Document the new endpoint and any new environment variables.
Write a small test or console log to confirm that cart updates appear in the visitors table.
By isolating the cart synchronization to a dedicated API route and a lightweight client effect, you can add persistent cart storage without altering the existing module plan. This keeps the upcoming modules (5‑8) focused on user authentication and session management while ensuring visitor carts are always saved and ready to merge when a visitor becomes a full user.

Module 6 Overview
Module 6 bridges visitor checkout into authenticated user checkout. It starts immediately after Module 5 (when the user opts to “Check out as user”) and concludes once Stripe’s checkout session is created. Modules 7–8 then manage Supabase session persistence, while Modules A–D handle the Stripe flow.
Module 6 Boundaries with Other Modules
Modules 7–8: Begin only after 6b or 6d completes. They rely on the Supabase session created or confirmed during Module 6 to handle ongoing session management and expiry.
Modules A–D: Assume the Stripe checkout session has been created in 6d. They process payment, handle webhooks, and manage post‑checkout steps.

6a. Session Short‑Circuit
Trigger: User chooses “Check out as user.”
Action: If a Supabase session already exists, skip the auth modal and create the Stripe checkout session using the session’s user ID.
Breakpoint: Confirm the call to /api/createCheckoutSession redirects directly to Stripe.

6b.1 – Merge Endpoint Setup
Trigger: A user finishes signing in or signing up via AuthModal.
Action:
Send a POST request to a new /api/user/merge route with the current visitor_id.
On the server, confirm the Supabase session and set user_id on the corresponding visitor row, merging cart and contact data.
Return a success response so the client can proceed.
Breakpoint: Verify that the endpoint correctly attaches the visitor row to the authenticated user_id and that the merged data is available.

6b.2 – Post‑Merge Cleanup and Checkout
Trigger: The merge endpoint responds successfully.
Action:
Clear visitor_id and the visitor JWT from localStorage.
Use the active Supabase session as the sole auth token.
Immediately call /api/createCheckoutSession with supabaseUserId to create the Stripe session.
Redirect the browser to the returned Stripe URL.
Breakpoint: Confirm visitor tokens are gone, the checkout session is created with the user’s ID, and Stripe redirection occurs without additional prompts.

Block 1: Convert Visitor Context to TanStack Query
Summary
The existing VisitorProvider keeps visitor ID, JWT, and visitor data in local useState variables. Initialization and cart synchronization rely on fetch calls. Converting this logic to TanStack Query ensures consistent caching and easier invalidation.
Where to Look
lib/contexts/VisitorContext.tsx — state initialization begins around lines 28‑31 and cart hydration around line 41. Fetch calls to /api/visitor/init and /api/visitor/validate appear near lines 140‑176, while cart syncing logic sits around lines 226‑251
Implementation Notes
Introduce a useQuery hook to fetch visitor data keyed by [ 'visitor', visitorId ].
Wrap cart updates in a useMutation so cart changes automatically invalidate visitor queries.
Maintain the context API (updateVisitorIdentity, syncCartToDatabase) so components do not need refactoring.
Guardrails
Keep the hook names and return shapes unchanged; components should receive the same values.
Do not alter the CSS classes controlling the popup or cart animations.
Bugwatch
After moving to queries, ensure window.location.reload() inside the invalid-JWT branch does not trigger infinite reloads if the query retries fail.

Block 2: Replace Ad‑hoc Fetch Calls with TanStack Queries and Mutations
Summary
Pages such as the checkout flow and layout still fetch products and trigger API endpoints with plain fetch calls. Replacing these with useQuery/useMutation ensures unified error handling and cache control.
Where to Look

components/Layout.tsx fetches products in an effect around lines 125‑133
Implementation Notes
Convert data retrievals (product lists, session checks) to queries with meaningful keys (e.g., [ 'products' ]).
Wrap POST operations (checkout session creation, visitor merge) in mutations that invalidate related queries upon success.
Keep query functions lightweight to avoid blocking UI transitions.
Guardrails
Preserve all modal behavior and page transitions exactly—loading indicators and success banners must still fire in response to the same events.
Keep local useState for UI toggles and simple form fields.
Bugwatch
When switching to queries, verify that dependency arrays or query keys do not create unwanted loops, especially around the checkout session creation logic.

Notes on Modules A–D: Existing Implementation
The Stripe-related modules already have partial support in the repository:
Module A – Checkout Session Creation
The route pages/api/createCheckoutSession.ts is implemented and creates a Stripe checkout session using items from the cart, with optional customerEmail and supabaseUserId parameters.
Module B – Webhook & Order Persistence
pages/api/stripeWebhook.ts listens for Stripe webhooks. It logs checkout or subscription events but the database operations are still marked as TODOs.
Module C – Success/Cancellation Handling
In pages/checkout.tsx, the code checks query parameters on page load. If success=1 is present, it clears the cart. This is a minimal success/cancel hook and does not yet show a detailed success page.
Module D – Customer Portal & Subscription Management
The API endpoints createCustomerPortalSession.ts and getSubscriptionDetails.ts are implemented to interact with Stripe’s billing portal and fetch subscription details. The dashboard.tsx page, however, uses hard-coded data rather than live Supabase or Stripe data, indicating this part is still a placeholder.
Overall, the groundwork for Modules A–D is present, but some database hooks and final UI pieces remain to be implemented once Module 6 and the user merge are fully integrated.
